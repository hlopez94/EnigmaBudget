# Recurrencias y cobertura médica Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add read-only recurring forecasts, explicit occurrence recording, and auditable healthcare expense settlement that separates gross consumption from bank cash.

**Architecture:** Versioned recurrence rules calculate stable scheduled-date identities without saving preview rows. A confirmed healthcare event remains one gross `FinanceOperation`; actual `FinancePayment` cash and append-only `NonCashSettlement` rows share `OperationSettlementCalculator`. Extend the existing stable Savings/Projection APIs and canonical card calculator; a linked `CardPurchase` carries card debt without double counting the operation-month budget contribution.

**Tech Stack:** .NET 10, EF Core, PostgreSQL, ASP.NET minimal APIs, Angular 22, OptimusUI 2, Vitest, Playwright.

**Spec:** `docs/superpowers/specs/2026-10-25-recurring-healthcare-design.md`; project constraints also come from `docs/superpowers/specs/2026-10-24-finanzas-design.md` and `docs/producto/funcionalidades-y-circuitos.md`.

## Global Constraints

- Angular 22 + OptimusUI 2 (the release compatible with Angular 22), .NET 10, PostgreSQL.
- One ASP.NET host serves the API and compiled Angular frontend. No Ionic or microservices.
- No private spreadsheet links, financial data, credentials, or tokens in this public repository.
- Amounts at API boundaries are decimal strings; PostgreSQL money uses `numeric(18,2)`.
- Enforce membership server-side; never trust a tenant ID or identity supplied by the client.
- Development sign-in is explicitly opt-in and forbidden outside Development. Google sign-in must fail closed when unconfigured.
- Spanish user-facing copy; ARS and USD remain separate.
- Check available RAM before builds/tests/browser suites/container builds; pause below 6 GiB. Run heavy processes sequentially, ≤4 GiB RAM/≤512 MiB swap; Node heap ≤2 GiB, Angular/Vitest workers ≤2, Playwright workers ≤1; container builds need a separate limit.
- Begin only after the controller integrates the catalog IDs/snapshots from `docs/superpowers/plans/2026-10-25-catalog-budgets.md`. Savings/Projection is already present at the approved base: reuse `ProjectionDto`, `ProjectionRowDto`, `ProjectionService.GetAsync/CalculateAsync`, `SavingsAccountBalanceQuery.GetAsync`, and `CardObligationCalculator.LoadAsync/Build`; do not wait for or edit unrelated Savings work.

## Review Focus

- Multiple overdue scheduled dates survive the bounded query and all have stable identities — Task 2 `overdue_occurrences_are_all_returned_per_date_with_pagination`.
- Monthly/leap-day schedule uses the original anchor rather than a clipped prior occurrence — Task 2 `monthly_anchor_does_not_drift_after_february`.
- The required health case is exact: 1,200 charge − 200 discount = 1,000 budget consumption; 300 verified applied payroll settlement + 700 cash payment = pending zero and bank outflow 700 — Tasks 3–4 `healthcare_1000_consumption_300_noncash_700_cash_pending_zero`.
- Noncash entries never create cash ledger, duplicates, tenant leaks, or over-settlement; a null operation account never hides pending cash from the projection — Task 3 `noncash_settlement_is_scoped_idempotent_and_has_no_ledger_entry` and `unassigned_pending_operation_is_projected_once_by_currency`.
- Operation void reverses cash once and appends noncash compensation without fake money — Task 3 `void_compensates_non_cash_history_and_reverses_cash_once`.

# Savings, Exchange Rates, and Projection Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add explainable savings reservations, DolarAPI rate snapshots, and per-workspace cash projections without changing the existing bank ledger or card-payment accounting.

**Architecture:** Add focused Savings, ExchangeRates, and Projection modules to the existing ASP.NET host. Savings reservations are append-only movements over account-backed allocations; projections derive a read-only, source-keyed view from current finance records and never post ledger entries. Angular exposes the modules from Más, using the existing workspace context, `ApiService`, finance action dialogs, and permission conventions.

**Tech Stack:** .NET 10, EF Core, PostgreSQL, ASP.NET minimal APIs, Angular 22, OptimusUI 2.

**Spec:** `docs/superpowers/specs/2026-10-25-savings-projection-design.md`; project constraints also come from `docs/superpowers/specs/2026-10-24-finanzas-design.md` and `docs/producto/funcionalidades-y-circuitos.md`.

## Global Constraints

- Angular 22 + OptimusUI 2 (the release compatible with Angular 22), .NET 10, PostgreSQL.
- One ASP.NET host serves the API and compiled Angular frontend. No Ionic or microservices.
- No private spreadsheet links, financial data, credentials, or tokens in this public repository.
- Amounts are decimal strings at API boundaries, stored as PostgreSQL `numeric(18,2)`; exchange rates use `numeric(18,8)` and a separate parser.
- Enforce membership server-side; never trust a tenant ID or identity supplied by the client.
- Use existing `WorkspaceRequestContext`, `recordFinance`, `manageResources`, `correctHistory`, and `readGroups` permissions. A shared PersonalReadGrant receives personal-goal read access but no group data or mutation permission.
- Spanish user-facing copy; all mutations validate CSRF, use UUID request idempotency, compare payload on replay, return 409 for a changed replay, and use version checks for editable resources.
- A savings allocation is backed by exactly one account currency amount. Allocating, releasing, applying, or reversing a reservation never creates a `LedgerEntry`.
- A recorded expense payment or card payment changes cash/debt only through its current finance flow. Reserve application only changes the reserved balance and must not create a second payment or ledger row.
- A projection is read-only and scoped to exactly one selected workspace. Reservations reduce free cash once at the projection start; they are not repeated daily expenses.
- Keep real user data on PostgreSQL port 55433 untouched. Automated integration fixtures may use only the test database on port 55432 and their isolated schemas.
- Before any later build, test, browser suite, or container build, check available RAM; pause below 6 GiB. Run heavy jobs sequentially through `work/with-ram-limit.sh`, keeping each process tree within 4 GiB RAM and 512 MiB swap. Node heap ≤2 GiB, Angular workers ≤2, Vitest workers ≤2, Playwright workers ≤1. Container image builds need their own memory cap.
- The public DolarAPI check is a separate opt-in integration check; deterministic CI uses a fake HTTP handler and never depends on network access.
- Use `work/with-ram-limit.sh work/tooling/dotnet/dotnet test ...` for .NET and `../work/with-ram-limit.sh env NODE_OPTIONS=--max-old-space-size=2048 npm test -- --maxWorkers=2` from `web/` for Vitest. For E2E use `../work/with-ram-limit.sh env NODE_OPTIONS=--max-old-space-size=2048 npm run test:e2e -- --workers=1` from `web/`; the wrapper enforces 4 GiB RAM, 512 MiB swap and a 6 GiB available-memory floor.

## Review Focus

- An attempted concurrent reservation against the same or multiple accounts must not make total reserved value exceed usable backing; prove with concurrent PostgreSQL requests in Task 3.
- A previously valid reservation can become under-backed after later cash spending; retain it, report nominal reserve, negative free amount and deficit, and reject new allocation; prove in Task 3.
- PersonalReadGrant must not disclose group receivables or permit goal/reservation writes; exercise both paths in Tasks 2 and 7.
- Card opening debt, installments, confirmed adjustments, carried components and payments must reconcile without adding statement totals or payment records a second time; exercise in Task 5.
- Unknown due dates and overdue unpaid items must remain visible and must not be silently assigned a confirmed date or removed by the horizon; exercise in Task 5.

# Diseño del primer slice Android y autenticación Google

Fecha: 25/10/2026  
Estado: diseño de construcción del próximo corte, revisado para planificar; no está implementado ni validado en dispositivo.  
Base de código: `c3e19f2`. El alcance es un primer corte Android dentro de la aplicación y del backend existentes; los módulos financieros y la validación externa continúan en el seguimiento del producto completo.

## Decisión recomendada

Crear un APK de depuración con Angular empaquetado y Capacitor mínimo, sin Ionic ni `server.url` de producción. Usar Credential Manager en Android para Google; el backend .NET valida el ID token y emite una sesión nativa opaca, revocable y separada de las cookies web. Mantener el login web actual sin cambio: cookie `HttpOnly`, `Secure`, `SameSite=Lax`, endpoint de sesión y antiforgery `X-CSRF-TOKEN` con cookie `SameSite=Strict`.

En `c3e19f2`, `ApiService` usa rutas `/api/...`, `credentials: 'include'` y CSRF en mutaciones; las rutas de finanzas añaden `X-Workspace-Id` capturado al despachar. El host ASP.NET registra Google solo con ID y secreto y responde 503 cuando el proveedor web no está configurado. Las rutas nativas deben ser opt-in por plataforma y no cambiar estos defaults web.

## Recorrido vertical

1. El APK incluye los activos de producción de Angular. La app configura una única URL base de API HTTPS por entorno y rechaza hosts no permitidos. `server.url` queda reservado a recarga local, jamás producción.
2. La UI invoca un plugin Capacitor Android pequeño. El plugin usa AndroidX Credential Manager y Google ID (`GetGoogleIdOption` y fallback `GetSignInWithGoogleOption`) con el `serverClientId` público del cliente OAuth web. Google recomienda Credential Manager en Android, el ID del cliente web como server client ID y validación en el backend; el flujo de Google no se inicia dentro de una WebView. [Implementación oficial de Credential Manager](https://developer.android.com/identity/sign-in/credential-manager-siwg-implementation) · [validación en backend](https://developers.google.com/identity/sign-in/android/backend-auth)
3. Antes de mostrar Google, Android pide al backend `POST /api/auth/native/challenge`. El servidor genera nonce criptográficamente aleatorio, lo ata a intento/plataforma, lo guarda con vencimiento breve y consumo único, y devuelve solo el valor necesario para `setNonce`. El plugin recibe el ID token; lo envía por HTTPS al endpoint de intercambio, no a una URL, logs o almacenamiento. Si no hay configuración Google, el flujo real falla cerrado con 503 y un mensaje localizable.
4. .NET verifica con una biblioteca mantenida (evaluar `Google.Apis.Auth.GoogleJsonWebSignature.ValidateAsync` con audiencia permitida explícita), además de comprobar igualdad exacta del nonce validado y consumir desafío y emitir sesión de forma atómica. La biblioteca valida firma Google, emisor, audiencia y tiempos; la versión revisada no expone un `Nonce` fuertemente tipado en `GoogleJsonWebSignature.Payload`, por lo que el implementador debe extraer el claim `nonce` solo del mismo token ya verificado o usar un validador que lo compruebe directamente. No decodificar un JWT sin verificarlo. Si esto no queda cubierto claramente por la biblioteca seleccionada y una prueba negativa de mismatch, no habilitar login Android. [Código y parámetros de validación de Google.Apis.Auth](https://github.com/googleapis/google-api-dotnet-client/blob/main/Src/Support/Google.Apis.Auth/GoogleJsonWebSignature.cs)
5. Resolver identidad por `(proveedor Google, sub validado)`; `sub` es clave estable, no correo, nombre, `email_verified` ni ID de cuenta provistos aparte por el cliente. Crear/actualizar datos de perfil solo desde claims verificados conforme a la política existente. El backend construye la identidad .NET; no acepta `userId`, tenant, rol o claims de usuario del móvil.
6. La respuesta de intercambio establece usuario y una sesión de dispositivo. Angular restaura la app llamando a `/api/auth/native/session`; el slice demuestra un GET protegido, una escritura protegida y logout/revocación. Membresía, espacio personal y permisos siguen saliendo del servidor. Cada endpoint existente continúa exigiendo la identidad y membresía server-side; `X-Workspace-Id` solo selecciona el espacio solicitado y nunca otorga acceso.

## Transporte de sesión elegido para Android

Usar credenciales **opacas aleatorias**, no JWTs propios ni ID tokens de Google como credenciales de API:

- Token de acceso opaco aleatorio y de vida breve (orden de minutos), enviado como `Authorization: Bearer` únicamente a la API HTTPS configurada. El servidor consulta la sesión revocable. RFC 6750 define el transporte Bearer; un token opaco evita claims de autorización almacenados en el cliente.
- Refresh token opaco, de mayor duración y un solo uso, rotado en cada refresh. Persistir en PostgreSQL solo hashes resistentes a búsqueda/inferencia (hash criptográfico de token de alta entropía), con sesión/dispositivo, expiración, token predecesor y estado revocado/consumido. Actualización atómica con transacción y concurrencia optimista/row lock. Reutilizar refresh consumido revoca la familia/sesión y obliga a autenticar de nuevo; logout revoca en servidor antes de limpiar el cliente. Definir expiración absoluta e inactividad razonables para MVP; no refresh indefinido.
- El acceso se puede invalidar al vencer; revocar sesión bloquea refresh y, como el token de acceso es opaco consultado contra sesión, permite revocación inmediata. Guardar en servidor digest/timestamps, nunca los valores secretos. No registrar cabeceras Authorization ni cuerpos de challenge/intercambio/refresh.
- No hay refresh paralelo: un coordinador nativo `single-flight` comparte un único refresh por sesión. La rotación y el uso del anterior deben ser atómicos en PostgreSQL; si el mismo refresh reaparece por concurrencia, tratarlo como replay y revocar. No intentar “reparar” ese error reutilizando el token anterior.
- Persistir credenciales solo en almacenamiento privado cifrado por una clave AES-GCM generada/no exportable en Android Keystore, a través de un plugin nativo pequeño. Keystore protege claves, no guarda directamente el refresh token. No usar `localStorage`, `sessionStorage`, Capacitor Preferences, SQLite sin cifrar ni URL. Limpiar borrador cifrado y memoria de credenciales en logout, revocación y cambio de cuenta. Un acceso token solo reside en memoria nativa mientras está vigente.
- **Transporte Angular:** suministrar un `Fetcher` móvil al `API_FETCHER` existente. El adaptador cruza al plugin nativo, que conserva la sesión y adjunta Authorization; JS recibe respuesta API, nunca refresh token ni acceso token. El plugin restringe solicitudes al origin HTTPS configurado y a `/api/`; no habilita navegación arbitraria. CapacitorHttp puede servir de base para HTTP nativo, pero no añade por sí solo la política de tokens; mantener el puente de sesión estrecho y comprobar que el comportamiento Fetch/respuesta no altere el contrato Angular. [API HTTP nativa de Capacitor](https://capacitorjs.com/docs/apis/http) · [Android Keystore](https://developer.android.com/privacy-and-security/keystore)

Tradeoff: más trabajo de backend y un plugin/transport propio frente a adaptar cookies cross-site; a cambio, la WebView no depende de cookies de terceros ni CSRF para bearer requests, y web mantiene sus cookies actuales. Las credenciales se aíslan de JS persistente, aunque una app empaquetada comprometida mientras está abierta aún podría abusar del puente o leer respuestas de finanzas; limitar API host/path, no cargar JS remoto y mantener logs sin secretos. El `HttpOnly` web sigue siendo preferible para navegador.

ASP.NET Core Identity API muestra un patrón oficial de acceso breve más refresh largo para clientes no-cookie, pero está dirigido a aplicaciones que adoptan Identity. Este repo no usa `IdentityUser`/`MapIdentityApi`; no añadir ese esquema solo para reutilizar esos endpoints. Mantener la identidad local existente y modelar el ciclo de sesiones nativas como módulo de la app. [Token API de Identity: tradeoffs y rotación](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/identity-api-authorization?view=aspnetcore-10.0) · [OAuth 2.0 Security BCP, RFC 9700](https://datatracker.ietf.org/doc/html/rfc9700)

## Aislamiento y orden de solicitudes

- Mantener un `authEpoch` local que sube al iniciar/cerrar sesión, revocar, expirar o cambiar usuario. Cada petición toma snapshot de época, usuario y workspace antes de iniciar un refresh; después de `ensureFresh`, descarta la petición sin red si cambió cualquiera de esos valores. Solo entonces manda el request al plugin. Nunca reanudar una operación de usuario A con las credenciales actuales de usuario B.
- Capturar el `X-Workspace-Id` al encolar el request y volver a confirmar que el workspace seleccionado no cambió luego del refresh; si cambió, abortar y volver a cargar desde el contexto actual. Enviar operaciones al host solo tras ese check final. El servidor verifica membership/privilegios en todo caso. Rechazar/limpiar cola pendiente al logout o cambio de identidad.
- Refresh serializado debe resolver antes de un único reintento de request que falló por 401 de autenticación y que el pipeline haya rechazado antes de entrar al handler. Nunca repetir automáticamente un write ante timeout, desconexión o resultado desconocido; mostrar estado recuperable y exigir recarga/confirmación para no duplicar movimientos.
- Native bearer no usa antiforgery cookie/token; el web cookie sí sigue validando antiforgery en todo POST/PUT/PATCH/DELETE. El challenge/exchange móvil debe llevar rate-limit, HTTPS, límites de tamaño, anti-replay de nonce y respuestas genéricas ante ID token inválido. CORS no es una autorización de Android.

## Restaurar, salir y enlaces de invitación

Al iniciar o volver al foreground, el plugin intenta refrescar/validar la sesión; Angular restaura `/api/auth/native/session` y luego perfil/espacios. Si refresh está vencido, revocado o repetido, elimina el almacén y vuelve al login sin mostrar datos anteriores. Logout invalida la sesión del servidor, borra claves/credenciales y limpia usuario, workspace seleccionado, requests en vuelo y datos en memoria. La expiración de la pantalla / datos debe mostrarse como sesión vencida, no conservar finanzas en caché local en este slice.

Para invitaciones usar Android App Links HTTPS de dominio propio y el manejo `appUrlOpen` de Capacitor. Mantener el secreto de invitación en el fragmento (por ejemplo `https://<dominio>/...#invite=<token>`), nunca query/path; los fragments no llegan al servidor HTTP. La app verifica host/ruta, captura el token temporalmente en memoria y lo retira inmediatamente del historial/vista; luego llama por POST al preview existente, pide confirmación explícita y POST de aceptación solo después del login. El enlace no selecciona workspace ni concede acceso por sí mismo. En web se mantiene el flujo existente `#invite=...` → sessionStorage por pestaña y limpieza de URL; Android no lo persiste en Preferences. No autounir ni mostrar el nombre/email del invitado como identidad verificada.

El dominio App Links debe servir `/.well-known/assetlinks.json` por HTTPS sin redirecciones, vinculado al package y certificado firmante SHA-256. El token Google nativo no usa estos enlaces: Credential Manager devuelve al plugin directamente; no hacer callback OAuth hacia la WebView. [Android App Links](https://developer.android.com/training/app-links/about) · [archivo de asociación](https://developer.android.com/training/app-links/configure-assetlinks) · [Capacitor App API](https://capacitorjs.com/docs/apis/app)

## Desarrollo, build y evidencia del slice

- `/api/auth/native/*` solo se configura con proveedor verificado y HTTPS en ambientes que lo tengan. Si falta client ID/audience esperado o configuración necesaria, responder no disponible; jamás degradar a confiar en correo/claims del cliente. Para desarrollo local se puede habilitar el endpoint de login de prueba existente solo si `ASPNETCORE_ENVIRONMENT=Development` y `Authentication:DevelopmentLoginEnabled=true`; prod y staging rechazan/not-found aunque llegue esa opción. Este endpoint no simula Credential Manager ni cuenta como prueba Google/dispositivo.
- Client ID OAuth: identificador público esperado/audience, el `serverClientId` puede ir en la app Android. El **client secret** del cliente Web usado por el handler ASP.NET actual es confidencial del servidor, nunca APK, Angular, config pública, salida de build o repo. No se creó Google Cloud project ni existe dominio elegido; no poner valores ficticios ni afirmar que login remoto, asociación App Links o Google está probado.
- Próxima etapa puede preparar configuración de empaquetado y build Android headless con APK debug, pero hoy faltan Android SDK/adb (según auditoría), device y credenciales Google; no instalar ni compilar como parte de esta nota. Antes de un build futuro: revisar RAM disponible (no iniciar si <6 GiB), ejecutar tareas pesadas secuencialmente y limitar árbol de proceso a 4 GiB + 512 MiB swap, heap Node 2 GiB y workers Angular 2; aplicar límite independiente al contenedor de imagen si se usa. No crear emulador bajo la restricción de RAM. El APK debug basta para distribución de validación, no hace falta decidir Play ni pagos.
- Evidencia necesaria en un teléfono real para cerrar el gate temprano: build instalado; login Credential Manager real contra proyecto configurado; nonce incorrecto/repetido rechazado; usuario y `sub` iguales al login web; restore tras cerrar/reabrir; GET protegido; mutación protegida; refresh concurrente sin cambiar usuario/workspace ni ejecutar dos writes; replay de refresh revoca; logout invalida server-side y limpia device; cancelar/ausencia de cuenta falla con recuperación comprensible; enlaces de invitación abren app y requieren confirmación con y sin sesión. No contar stubs, mocks o solo emulador como prueba real del proveedor.

## Prerrequisitos externos que bloquean prueba real

1. Proyecto Google Cloud propiedad/control del usuario y configuración OAuth consent. Crear cliente Android asociado al package y huella SHA-1 del certificado debug; crear cliente Web/server cuyo ID sea la audiencia de Credential Manager y guardar su secreto solo fuera del APK en configuración ASP.NET. Identidad/cuenta real de prueba autorizada mientras consentimiento esté limitado a testing. No hay proyecto actualmente: hasta entonces solo cabe preparar integración/compilación, no declarar login Google verificado. El backend ASP.NET existente usa `Authentication:Google:ClientId` + `ClientSecret` para Google web; conservarlo sin secreto en el repo.
2. Hostname público estable y certificado HTTPS para API. Para verificación end-to-end de App Links de invitación: dominio propio controlado, publicación directa de `assetlinks.json` con package/fingerprint SHA-256 del APK firmado; la SHA-256 de enlaces y SHA-1 para registrar cliente OAuth son huellas distintas. No existe dominio elegido hoy, así que resolver App Links en teléfono requiere esa decisión/despliegue.
3. Un teléfono Android físico con versión/Google Play Services compatibles y USB/adb habilitado, obtenido después de disponer del SDK. La auditoría no halló SDK, adb ni dispositivo; no se sustituyeron por un emulador.

Package name, estructura del plugin, endpoints exactos, esquema de sesiones y TTL son decisiones reversibles del constructor antes de publicar. No fijar package final de Play sin aprobación si ya se llegara a publicar; APK inicial no requiere adoptar Play. Canal release, Play billing y políticas de compra quedan fuera del slice.

## Decisiones concretas de construcción

Estas son decisiones reversibles de construcción, no acuerdos comerciales nuevos:

- La validación local Android sin proyecto Google necesita una ruta de prueba que emita la misma clase de sesión nativa opaca. Preparar POST /api/auth/native/development con el mismo Key y allowlist de identidades sintéticas que el login web, solo en Development con login de desarrollo y un opt-in nativo adicional; ruta inexistente fuera de Development aunque estén configuradas opciones. No usar la cookie del endpoint web como si fuera un token nativo ni presentar esta ruta como éxito Google. Producción conserva fail-closed.
- Valores iniciales configurables del servidor: desafío de dos minutos, acceso de cinco minutos y sesión/refresh con vencimiento absoluto de treinta días. Ningún refresh extiende ese límite absoluto. Single-flight del cliente y consumo atómico del servidor; pérdida de respuesta de refresh obliga a reingreso en lugar de reutilizar un refresh consumido. Las pruebas distinguen error de red de confirmación financiera y conservan IDs de reintento para resultados desconocidos.
- El puente nativo HTTP admite solo el origen API configurado y rutas /api/, sin seguir redirecciones externas ni reenviar Authorization a otro host. El primer corte puede soportar JSON y rechazar otros cuerpos explícitamente; el módulo de archivos posterior debe completar streaming/binario antes de declarar Android completo. Tokens nunca se entregan como respuesta al JavaScript de la aplicación; el plugin conserva y aplica la credencial.
- Nuevos enlaces de invitación usarán una ruta específica /invitar con token en fragmento. Mantener enlaces web antiguos /#invite=... funcionando. El filtro App Links del APK se limita a /invitar, sin capturar /signin-google ni todo el dominio; así no intercepta el callback web del proveedor. Dominio y archivo assetlinks siguen pendientes de configuración real, sin promesa de asociación probada.
- La primera firma/paquete son de APK debug para validar, sin publicación Play. Elegir un identificador de aplicación de desarrollo y documentarlo; no crear recursos de Google, DNS ni publicar paquetes sin los datos reales. Preparar compilación headless con límite de memoria, sin emulador.

El builder check no encontró preguntas de arquitectura pendientes que impidan planificar. La prueba real de proveedor/dispositivo sigue pendiente de sus insumos externos y no se reemplaza por mocks. Al mapear la identidad, mantener el valor sub validado sin prefijos nuevos en ClaimTypes.NameIdentifier, conforme a CurrentIdentity.Subject existente; web y Android deben resolver el mismo ApplicationUser y Personal. API_FETCHER existe en la base, pero se deberá exportar o reubicar su InjectionToken para poder configurar el adaptador nativo sin duplicar ApiService.
